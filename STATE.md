## What this is

A single-file browser screensaver: `index.html` (~555 lines, vanilla JS,
no build step, no dependencies). It fakes a Commodore 64 boot sequence
(`**** C64 BASIC V2 ****`, `LOAD "CHUNKY-MATRIX",8,1`, PETSCII load-noise)
that transitions into a Matrix-style character rain rendered in a chunky
C64-style grid, using a custom bitmap font. There's a looping soundtrack
and tap/hold controls to cycle through the 16 C64 Pepto palette colors for
head/background/frame.

Deployed via GitHub Pages from the `main` branch root:
- Live: https://polerix.github.io/ChunkyMatrix/
- Repo: https://github.com/polerix/ChunkyMatrix

Origin: the C64 6502 assembly algorithm was generated by Claude Fable 5.1
(per README) and the browser port is a line-for-line translation of that
algorithm's cell logic (erase/dim/body/trail/head — 5 cells touched per
column per step).

## Architecture (all in `index.html`)

- **One IIFE**, no modules, no build. Canvas `#matrix-cvs` inside a
  `#c64-frame` > `#c64-screen-wrapper` DOM structure that mimics a C64
  monitor bezel. `#colour-hint` also lives inside `#c64-screen-wrapper` now
  (moved there this session — see mobile fixes below).
- **State machine** (`bootState`) drives everything through one
  `requestAnimationFrame` loop (`tick()`):
  `init → waiting → typing → searching → found → loading → ready → rain`
  Boot text and the rain reuse the *same* grid/cell/font machinery
  (`drawCh`, `printAt`/`printLine`, `grid[][]`) — this was a deliberate
  "unified single canvas" decision (commit `d1a0441`), not two separate
  renderers.
- **Font**: self-hosted `BoutiqueBitmap9x9_Bold.ttf` (checked into repo,
  ~2.1MB), loaded via `document.fonts.load()` before boot starts, with an
  off-screen warm-up `fillText` to force glyph rasterization.
- **Sizing**: `chunkSize(W,H)` takes the drawable width AND height in CSS
  px (the `#c64-screen-wrapper` rect, not `window.innerWidth`) and derives
  cell width from a target column count that scales with `W`, clamped to
  `[24, 34]` columns, THEN shrinks further if needed so height still gives
  at least `MIN_ROWS=16` rows (a short landscape viewport sized purely
  from width could otherwise starve `ROWS`). Guarantees the 22-char boot
  header always fits with margin at any width down to 320px and any
  height down to ~250px tested, while staying "chunky" (not shrinking to
  normal terminal density) on a large desktop window.
- **Boot row layout**: `computeBootRows()` sets `ROW_HEADER`/`ROW_RAM`/
  `ROW_READY`/`CMD_ROW` from `ROWS` — the authentic spacing (rows 2/5/7/9)
  when `ROWS>=10`, compressed proportionally otherwise. Was hardcoded
  literals before this session; that's what made a short landscape boot
  screen render almost nothing (fixed rows fell outside `ROWS` and
  silently didn't draw — `drawCh` bounds-checks and no-ops out of range).
- **DPR handling**: `resize()` sizes the canvas *backing store* to CSS px
  × `devicePixelRatio` and applies `ctx.setTransform(dpr,0,0,dpr,0,0)` —
  the ONLY place DPR enters the picture; everything else (`CELL_W/H`,
  `CSS_W/H`, all draw coordinates) stays in CSS px. `#matrix-cvs` also
  needs explicit `width:100%; height:100%` in CSS alongside `inset:0` —
  canvas is a replaced element, so `inset:0` alone does NOT stretch it to
  fill its container; without the explicit size it falls back to its
  *intrinsic* size, which for canvas is its width/height ATTRIBUTES (the
  DPR-scaled backing store!), making the on-screen box `devicePixelRatio`×
  too large. This was the real bug behind the "still broken on a real
  iPhone" report — see below, don't remove that CSS rule.
- `resize()` returns `false` and touches no state if the wrapper is still
  a 0×0 rect (see crash-fix section below) — callers must check this.
- **What triggers `resize()`**: a `ResizeObserver` on `#c64-screen-wrapper`
  (NOT a `window resize`/`orientationchange` listener — round 3 found
  those fire before Safari's dynamic toolbar/safe-area has settled into
  its final size, especially post-rotation, leaving `CSS_W`/`CSS_H` stale
  relative to the wrapper's true final size). Falls back to a `window
  resize` listener only if `ResizeObserver` doesn't exist (essentially
  never, in 2026). A `requestAnimationFrame`-deferred extra `resize()`
  call rides along as a one-more-frame settle backstop.
- **`COLS`/`ROWS` use `Math.floor`, not `Math.ceil`** — round 3 found real
  overflow (`COLS*CELL_W` exceeding the canvas's actual CSS width) from
  the old ceil. Floor leaves at most one cell of solid background at the
  far edge instead; never draws past the edge. `chunkSize`'s column clamp
  guarantees this can't drop `COLS` below the 22-char-header floor.
- **`?debug=1`**: on-screen readout (top of viewport, semi-transparent so
  the rendering underneath stays visible) of every width/height signal in
  the layout chain — devicePixelRatio, innerWidth/Height, visualViewport,
  wrapper rect + clientWidth, canvas CSS size vs backing store, CELL_W/H,
  COLS/ROWS, bootState. Polls every 1s as a backstop. Zero effect without
  the query param. Permanent diagnostic tool, not a one-off — keep it. It
  is, as of round 3, the thing that actually found both real bugs; trust
  its numbers over any emulated test in this repo.
- **Rain**: each column is `{x, row, speed, delay, len, band}`. `band` is
  `x % 4` (4 groups); `updateMatrix()` gives each band an identical phase
  offset so columns in the same band crest together — a real synced-wave
  effect, not a per-column gradient (see "Experimental — needs your eyes"
  below, this is v1 and may need tuning).
- **Palette**: 16-color C64 "Pepto" palette. Tap-to-cycle: tap a glyph →
  cycle head color; tap empty cell → cycle background; tap the frame border
  → cycle frame color. Short tap = one step. Hold >500ms → fast-cycle at
  150ms/step, additive on top of the single-tap behavior.
- **Controls strip**: checkboxes for CJK glyphs, ASCII glyphs, "SIG"
  (Space Invader sprite glyphs), and sound on/off.
- **Discoverability hint**: `#colour-hint` fades in when rain starts,
  fades out 5s later. Now `position:absolute` inside
  `#c64-screen-wrapper` (was `position:fixed` on the viewport — see mobile
  fixes below).
- **Audio**: `soundtrack.mp4` (~17.7MB, checked into repo directly, not
  Git LFS) as a looping `<audio>` element, gated behind a user gesture
  (autoplay policy) and the SND checkbox.

README.md does not track any of this — see "Known stale" below.

## Fixed this session (round 2): the REAL mobile bug — canvas box sizing

Round 1 (`c19602d`) fixed a genuine bug (flat desktop-tuned cell-size
divisor) but introduced DPR-scaling for the canvas backing store
(`cvs.width = CSS_W * devicePixelRatio`) without realizing that alone
creates a NEW, worse bug: **`#matrix-cvs` is a replaced element.**
`position:absolute; inset:0;` does NOT stretch a replaced element to fill
its container — without explicit `width`/`height` in CSS, it falls back
to its *intrinsic* size, which for `<canvas>` is its width/height
**attributes**. Those attributes were now the DPR-scaled backing store
size, so the on-screen CSS box became `devicePixelRatio`× too large (2x
at DPR2, 3x at DPR3), clipped by the wrapper's `overflow:hidden`. That's
"double DPR" in effect — once correctly for backing-store resolution,
once more (unintentionally) for the on-screen box — and it exactly
explains all four of PAUL-ERIC's screenshots: header truncated (only the
un-clipped fraction of an oversized, off-position render was visible),
rain clipped mid-glyph past the right edge, landscape rows clipped by the
HUD, landscape boot showing almost nothing (only the top-left corner of
a 2-3x-oversized canvas was inside the visible wrapper).

**This also explains the false-pass in round 1's verification.** The
"ink stripe" check read pixels from the canvas's own backing-store
buffer via `getImageData` — internally self-consistent (the drawing
*inside* the buffer was correct) but structurally blind to whether the
canvas *element* was the right size on the page. It could never have
caught this bug. Replaced it with a real geometric assertion: rendered
cell pitch (`CELL_W`) × `COLS` checked against the canvas's actual
on-screen CSS width, independently measured via `getBoundingClientRect`
(not the app's own internal `CSS_W` — that would just check the app
agrees with itself), same vertically, plus an explicit
wrapper-bottom-above-controls-top check for HUD overlap. Confirmed this
assertion actually discriminates (not a rubber stamp) by simulating the
old bug (`width:auto;height:auto`) and watching it fail loudly before
fixing it for real.

Fix (commit `78822a5`, full detail in the commit message):
1. `#matrix-cvs { width:100%; height:100%; }` added alongside `inset:0` —
   forces the CSS box to track the wrapper regardless of the backing-store
   attribute values. This is the actual fix.
2. `chunkSize(W,H)` now also constrains cell size by height
   (`MIN_ROWS=16`), not just width — a short landscape viewport sized
   purely from width could get a cell tall enough to starve `ROWS`.
3. `computeBootRows()` makes boot row positions relative to `ROWS`
   instead of hardcoded `2/5/7/9` — fixes the "landscape boot shows
   almost nothing" report (those rows were silently out of bounds).
4. Added `?debug=1` — see Architecture section above. Ship this
   regardless of whether the CSS fix alone was sufficient; it's the tool
   that will catch the *next* one of these.

**Verified in emulation** (Chrome, this session): geometric assertion
passes at DPR 1/2/3 (DPR 2 real emulation; 1 and 3 via
`Object.defineProperty(window,'devicePixelRatio',...)` + dispatched
`resize` — same `resize()` code path, no DPR-specific branching to miss),
portrait 393×852, landscape 852×393, and an extreme landscape 844×320.
Zero console errors throughout. **Not yet confirmed on PAUL-ERIC's actual
iPhone** — that's the next step, via `?debug=1`, not another round of

**Earlier verification caveat, still true**: this session's browser pane

## Fixed this session (round 3): stale CSS_W/CSS_H from window 'resize'

PAUL-ERIC's `?debug=1` readout from his iPhone 17 Pro (DPR3) after round 2
shipped: canvas CSS size now correctly equalled the wrapper in both
orientations (round 2's fix held) — but `CSS_W`/`CSS_H` ("what resize()
measured") disagreed with a fresh `getBoundingClientRect()` of the SAME
wrapper element, read moments later in the same debug line:

- Portrait: measured 254×712, actual (per the wrapper's own rect, same
  readout) 378×634.
- Landscape: measured 708×610, actual 708×272 — width right, height very
  wrong.

Root cause: `window.addEventListener('resize', () => resize())` fires
when the browser dispatches the event, which is not guaranteed to be
*after* the layout is done changing. On iOS Safari specifically, the
dynamic toolbar/safe-area can still be animating/settling into its final
size when `resize` fires — especially right after an orientation change —
so `resize()` captured a transient, not-yet-final layout and then simply
never got called again once the toolbar finished settling (no further
`resize` event fired for that).

This was consequential, not cosmetic: `COLS`/`ROWS` (and everything drawn)
were being computed against the WRONG `CSS_W`/`CSS_H`, independent of the
round-2 canvas-box-size bug. Portrait: `COLS*CELL_W = 260` against an
actual 378px-wide canvas — 118px of dead space, matching "rain columns
stop about two-thirds across." Landscape: `ROWS*CELL_H = 624` crammed into
a 272px-tall canvas — only ~10 of 24 computed rows fit, matching "thin
band of rain and nothing else."

Fix: replaced the `window resize` listener with a `ResizeObserver` on
`#c64-screen-wrapper`. `ResizeObserver` is specified to fire strictly
after layout, reporting the box's actual settled size — the right signal
structurally, not a heuristic that happens to usually correlate with it.
Chose the wrapper over the canvas to avoid the canvas's own `width`/
`height` attribute writes (inside `resize()`) potentially self-triggering
notifications. Kept a `requestAnimationFrame`-deferred extra `resize()`
call riding along as a backstop for a possible further single-frame
settle.

Separately, same commit: `COLS`/`ROWS` switched `Math.ceil`→`Math.floor`.
The landscape readout showed `COLS*CELL_W=720` against a 708px canvas —
real overflow past the edge, not a rounding nicety. Verified this can't
regress the 22-char-header-fit requirement: `chunkSize`'s column clamp
guarantees `CSS_W/cw >= targetCols(>=24)` by construction, so
`floor(CSS_W/cw) >= 24` always holds.

**Verification, and its limits.** Replicated the exact reported device
readings in emulation (402×676 portrait, 750×338 landscape, DPR3
override) and drove a full rotation cycle (portrait→landscape→portrait),
asserting after each: `CSS_W`/`CSS_H` exactly matches a fresh
`getBoundingClientRect()` of the wrapper (the precise mismatch reported),
and `COLS*CELL_W`/`ROWS*CELL_H` never exceed the canvas's actual CSS size.
Passed, both directions. Hit yet another instance of this session's
recurring pane-hidden-throttling problem while testing: the
`ResizeObserver` notification for a `resize_window`-tool-driven viewport
change took ~25s to arrive while the pane was backgrounded. Ran a control
test first — a plain `ResizeObserver` on a directly-`style`-mutated test
div fired within 200ms in the same hidden pane — which shows `RO` isn't
universally suppressed there, just unusually slow for this specific
viewport-driven delivery path while backgrounded. Not expected to
reproduce on an actively-viewed real screen (nothing throttles rendering
for a page someone is actually looking at), but this is exactly the kind
of gap between "emulation says X" and "device says Y" that's bitten this
project twice already — flagged, not asserted away. **The mechanism is
verified correct; its timing on a real, foregrounded device is not
something this harness can measure, and only the next on-device
`?debug=1` readout settles it.**

## Fixed this session (part 1): boot-freeze crash (root cause)

`resize()` ran once when `document.fonts.load()` resolved. On both the
live deployed site and a fresh local load, `#c64-screen-wrapper
.getBoundingClientRect()` sometimes returned a **0×0 rect** at that exact
moment — a real layout-timing race, not a viewport-width thing. That made
`COLS`/`ROWS` both `NaN` (`0/0`) and left `grid` as an empty array.

The bounds guard in `drawCh` — `if(col<0||col>=COLS||row<0||row>=ROWS)
return;` — is silently `false` for *every* comparison against `NaN`, so it
didn't catch this. `startBoot()`'s first `printAt` call then executed
`grid[NaN][2] = ch`, threw, and since `requestAnimationFrame(tick)` was
the next line in the same callback, **the animation loop never started**.

Fix (commit `2ac0f30`): `resize()` returns `false` and touches no state on
a 0×0 rect, retrying via `requestAnimationFrame`; all four bounds checks
flipped to positive-AND form so a stray `NaN` can't slip through again.

## Settled decisions (don't re-litigate)

- Single unified canvas/grid for both boot text and rain, not two
  renderers (`d1a0441`).
- CRT scanline/vignette overlay was tried and explicitly removed
  (`4c49887`) in favor of just the soundtrack.
- No build step, no framework, no bundler. Stays a single `index.html`.
- Binary assets (font, soundtrack) are committed directly to the repo, not
  via Git LFS or an external CDN — flagged, not yet decided on.
- 16-color "Pepto" C64 palette is fixed/canonical.
- Boot single-line text (header, "64K RAM SYSTEM", "READY.") uses
  `printLine()` (truncates, never wraps) instead of `printAt()` (wraps) —
  keep using `printLine` for any new boot text landing on an exact row.
- Cell sizing is `chunkSize(W,H)` keyed off actual drawable width AND
  height, target column count clamped `[24,34]`, height-constrained to
  `MIN_ROWS=16` — don't reintroduce a flat px-per-cell divisor or a
  width-only formula, both are exactly what broke on real phones.
- Canvas backing store is DPR-scaled (`CSS_W/H * devicePixelRatio`); any
  new code drawing to the canvas should keep using CSS-px coordinates
  (`CELL_W`, `CSS_W`, etc.) — the `ctx` transform handles the rest. Don't
  read `cvs.width`/`cvs.height` for layout math, they're device-px now.
- **`#matrix-cvs` MUST keep explicit `width:100%; height:100%` in CSS,
  alongside `inset:0`.** Canvas is a replaced element — removing that rule
  reintroduces the real mobile bug (on-screen box falls back to the
  DPR-scaled backing-store attribute size, `devicePixelRatio`× too large).
  This is not redundant with `inset:0`, don't "simplify" it away.
- Boot row positions (`ROW_HEADER`/`ROW_RAM`/`ROW_READY`/`CMD_ROW`) are
  set by `computeBootRows()` from `ROWS`, not hardcoded — needed for
  short (landscape) viewports. Any new boot text with a fixed row should
  go through something similar, not a bare literal.
- Verify canvas/CSS-sizing bugs with a real geometric assertion (rendered
  content size vs `getBoundingClientRect`, independently measured) — a
  `getImageData`/ink-stripe check of the canvas's own buffer is blind to
  on-screen box-size bugs by construction, proven by false-passing this
  exact bug in round 1.
- **Sizing is driven by `ResizeObserver` on the wrapper, not `window
  resize`/`orientationchange`.** Don't revert to an event listener —
  those can fire before iOS Safari's dynamic toolbar has settled into its
  final size, which is exactly what round 3 was.
- `COLS`/`ROWS` use `Math.floor`, never `Math.ceil` — content must never
  exceed the drawable CSS area, a few px of background margin at the edge
  is fine, overflow past the edge is not.
- `#colour-hint` lives inside `#c64-screen-wrapper` as `position:absolute`
  — don't move it back to a viewport-fixed position, that's what caused
  the HUD collision on mobile.
- Band-sync is genuinely experimental — don't treat the v1 constants as
  final without feedback.
- This session's browser pane can serve stale `screenshot` composites for
  canvas content when backgrounded — prefer direct state reads
  (`getImageData`, or a temporary debug hook) over screenshots when
  verifying canvas-rendered content in this environment.
